Codex, Claude Code and pi all face the same budget: a fixed number of tokens per request, and a session that wants more. They spend it differently. This is a parts-level reading of how, from source code and a shipped binary, with the constants that actually ship.

*November 2026 · Codex `748ab55` · pi-mono `5ea81d2` · Claude Code 2.1.317, constants re-checked on 2.1.319*

<TD id="gauge" />

A coding agent's context window fills up. Every harness answers with the same four moves: cap what tools return, summarize the history when it gets long, keep the start of the prompt unchanged so the cache holds, and write the session to disk. All three subjects here do all four. On a 200K window their compaction alarms even go off within 17,000 tokens of each other, as the scale above shows.

The differences are in what each one trusts to hold the state that no longer fits.

<TD id="creeds" />

### What the reading turned up

1. **When a harness compacts matters less than what it keeps.** The triggers are close. What survives is not: recent user messages only (Codex), a short tail plus files re-read from disk (Claude Code), or a 20,000-token tail of everything (pi).
2. **One trigger is a fraction and two are fixed reserves**, so they drift apart as windows grow. On a 1M window Codex compacts at 900,000 tokens and pi at 983,616.
3. **All three append and never edit.** New tools, new servers and changed instructions arrive as later messages, so the cached prefix survives. Compaction is the one deliberate exception.
4. **pi's cache warming almost never fires while you're away.** By its own formula, at $3 per million input tokens and a 5-minute cache, a refresh pays only above roughly 230K tokens of context.
5. **How tool output is cut may decide how often compaction runs.** In the model at the end of this page, Claude Code compacts about half as often as the other two. That result rests on assumptions that favor it, stated there, and has not been measured.

### How to read the figures

Thresholds, caps, prompts and formulas are quoted from source or from the binary, and tagged: <span class="td-ev">src</span> read in source code, <span class="td-ev">bin</span> found in the shipped binary, <span class="td-ev">docs</span> stated in official documentation. Sessions, block sizes and costs in the figures are a model I wrote, tagged <span class="td-ev">model</span>. With one exception in the compaction section, nothing here was measured on a real task.

Unless a control says otherwise, everything is compared on a 200K window at the same prices. That isolates the harness, but it is not how the tools ship: Codex's bundled models default to a 272K window, and Claude Code can run at 1M. The first two figures let you change the window.

## Where the alarm goes off

The first decision any harness makes is when to stop and shrink the history. All three compute a token threshold from the model's context window, but the formulas differ in kind, not just in degree.

<span class="td-h cx">Codex</span> uses a fraction: auto-compaction fires at 90% of the window, or at the user's configured limit if that's lower <span class="td-ev">src</span>. It also treats only 95% of the window as usable, so there's a hard ceiling at 95%. <span class="td-h pi">pi</span> uses a fixed reserve: compact when context exceeds the window minus 16,384 tokens <span class="td-ev">src</span>. <span class="td-h cc">Claude Code</span> stacks two deductions: first it subtracts room for the model's reply (the smaller of the max output setting and 20,000), then it compacts 13,000 tokens below that <span class="td-ev">bin</span>. It also has a warning band 20,000 below the trigger and refuses new requests within 3,000 of the effective window.

The difference matters most at the extremes. A fraction scales with the window, so on a 1M-token model Codex still keeps 100K tokens of headroom. A fixed reserve doesn't: pi on the same model lets the context run to 983,616 tokens.

Each harness also checks at different moments. Codex checks before a turn, in the middle of a turn (between tool calls) and after it. pi checks between turns after tool results, before sending a new prompt, and once more as a recovery path: if the provider rejects a request for overflowing, or the reply stops early with a length error, pi compacts and retries <span class="td-ev">src</span>. Claude Code adds a circuit breaker: if the context refills to the limit within 3 turns of a compaction, 3 times in a row, it stops and tells you that auto-compact is thrashing <span class="td-ev">bin</span>.

### How full is it, really?

None of the three runs the model's tokenizer locally, so the number each trigger is compared against is partly a guess. Codex and pi use the same method: take the token count the server reported with the last response, and add an estimate for everything added since, at 4 bytes per token for Codex and 4 characters per token for pi <span class="td-ev">src</span>. Claude Code also estimates from a bytes-per-token ratio <span class="td-ev">bin</span>.

The anchor is exact and only the tail since the last response is guessed. That tail is usually small. It is large right after a tool returns 80KB of minified JSON, which is when the decision matters most. Dense content packs more tokens into each byte than the estimate assumes, so the real count runs ahead of the harness's belief. pi's version is further off for Chinese, Japanese and Korean text, because one such character is three bytes and pi counts characters.

Each harness has a backstop. pi treats a provider's overflow error as a signal to compact and retry once. Codex's remote compaction path first swaps the newest oversized tool outputs for a short note if the history still doesn't fit. Claude Code's 3,000-token blocking margin and 13,000-token buffer work as error bars.

## The shape of a request

A prompt cache only rewards an unchanged prefix. The moment one early byte changes, everything after it is reprocessed at full price. So the most important structural question is where each harness puts things that change.

The three layouts look different on the wire. <span class="td-h cx">Codex</span> sends no separate system prompt at all: the base instructions are the first developer message in the input, followed by one bundled developer message (permissions, tool namespaces, skills), then a user message with the environment and AGENTS.md text <span class="td-ev">src</span>. <span class="td-h cc">Claude Code</span> splits its system prompt at a literal marker, `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__`. The part before it is cached with a "global" scope, the part after with an organization scope <span class="td-ev">bin</span>. Environment, date, skill listings and about 80 other kinds of reminder arrive later as messages. <span class="td-h pi">pi</span> builds its system prompt from tagged sections and, when one changes, appends a patch as a later system message instead of editing the first one <span class="td-ev">src</span>.

Underneath, they agree on the rule: never rewrite the past. Try the events below.

<TD id="f-req" />

Three events end up appended in all three harnesses. A newly connected MCP server becomes a delta message in Codex, a `deferred_tools_delta` attachment in Claude Code, and an appended `mcp_servers` section patch in pi, whose docs say it's done "so earlier messages stay cached". Loading a tool on demand also appends: Codex puts the definitions into the input as a tool-search result rather than changing the `tools` array, and pi uses Anthropic's `tool_addition` blocks for the same reason. Switching models costs everyone the whole cache, because caches are per model.

Compaction and clearing old tool results are the deliberate exceptions. They trade one expensive cache rewrite for a much shorter context afterwards. Only Claude Code does the second kind.

## When a tool talks too much

A test suite that prints 200KB of logs can fill a fifth of a window in one call. All three harnesses cap tool output, and they disagree about which part of the output to keep.

- <span class="td-h cx">Codex</span> keeps both ends. The default limit is 10,000 tokens (estimated as 4 bytes each), split 50/50 between head and tail, with `…N tokens truncated…` in the middle and a header with the original size <span class="td-ev">src</span>.
- <span class="td-h cc">Claude Code</span> keeps the start. Bash output over 30,000 characters is written to a file; the model gets a 2KB preview and the path, and can read the rest if it wants to <span class="td-ev">bin</span> <span class="td-ev">docs</span>. I tried it: a 107KB command output came back as a 2KB preview of the start.
- <span class="td-h pi">pi</span> keeps the end for `bash`: the last 2,000 lines or 50KB, whichever is smaller, plus a note with the full output's temp-file path <span class="td-ev">src</span>. Its `read` tool keeps the start instead.

Which one is right depends entirely on where the important line is. Move the error around.

## Compaction, frame by frame

Every harness compacts by asking a model to summarize the history and then building a new, shorter history around that summary. The interesting part is what survives verbatim, because a summary is lossy and everything kept verbatim isn't.

<TD id="f-compact" />

<span class="td-h cx">Codex</span>, compacting locally, rebuilds the history as: a fresh copy of its initial context, then the most recent *user* messages up to 20,000 tokens (newest first, older ones dropped once the budget runs out), then the summary <span class="td-ev">src</span>. No assistant message, tool call or tool result survives. The theory is clear enough: what the user asked for is the one thing you can't reconstruct, and everything else is in the summary or on disk.

On OpenAI's own providers Codex doesn't summarize locally at all. It sends a normal request with a special compaction-trigger item appended, and the server returns an encrypted compaction item that replaces the history <span class="td-ev">src</span>. The client never sees the summary text. What Codex keeps alongside it is larger: user messages and some agent and developer messages, up to 64,000 tokens.

<span class="td-h cc">Claude Code</span> keeps very little conversation: a short tail of the most recent messages, placed after the summary with a note that they are "kept verbatim" <span class="td-ev">bin</span>. I don't know the rule that sizes the tail. Most of what it restores comes from disk instead: up to 5 recently touched files at up to 5,000 tokens each, invoked skills (5,000 tokens each, 25,000 total), the plan, project CLAUDE.md and the skill listing <span class="td-ev">bin</span> <span class="td-ev">docs</span>. It reads the files again rather than keeping old tool results, so they are current, not whatever was true when the result was recorded.

<span class="td-h pi">pi</span> keeps the most conversation. It finds a cut point so that at least 20,000 tokens of the most recent messages stay as they were, tool results included, and summarizes everything before it <span class="td-ev">src</span>. If the cut lands inside a turn, it writes a second, smaller summary of that turn's beginning and merges the two. The summary also carries running lists of files read and modified.

> **One measurement.** The session that produced this page ran in Claude Code on a 1M-token window, and its session file records one compaction, started by hand. Context went from 301,772 tokens to 16,303 in 30.7 seconds, with two messages kept verbatim. The next request was still about 196,000 tokens. Everything that isn't conversation gets attached again, and in that session, which had an unusually large number of MCP tools connected, the list of deferred tool names alone ran to roughly 490,000 characters. This is one session and one compaction, so read it as an example of the mechanism and nothing more.

## What the summarizer reads

The prompts tell you what each team thinks a handoff needs. Here are their structures, quoted from the source and the binary.

<TD id="prompts" />

The inputs differ as much as the prompts. Codex and Claude Code hand the summarizer the history as conversation items. pi serializes it into plain text first: `[User]:` and `[Assistant]:` lines, thinking dropped, and every tool result cut to 2,000 characters <span class="td-ev">src</span>. The summarizer reads far less, which makes compaction cheaper and faster, at the cost of never seeing the bulk of what tools returned.

<TD id="f-sumin" />

The update prompt deserves more attention than it gets. Most harnesses re-summarize a history that already contains the previous summary, so details pass through the summarizer again each time and can be paraphrased away. pi passes the previous summary in separately, inside `<previous-summary>` tags, with explicit instructions to keep it and edit only what changed.

## Idle time and the cache clock

Anthropic's prompt cache lasts 5 minutes or 1 hour after the last read. When you walk away from an agent, the cache expires, and the next request pays the write price on the entire context again. Two of the three harnesses have opinions about this, and they are opposites.

<span class="td-h pi">pi</span> tries to keep the cache warm. While idle, it can send a refresh request at 90% of the cache lifetime, if the expected saving is at least $0.05 and you've been idle less than 30 minutes <span class="td-ev">src</span>. The expected saving is computed with a measured constant: a 15% chance that you'll come back before the cache expires.

<span class="td-h cc">Claude Code</span> does the reverse. After 3,900 seconds idle, it clears the content of old tool results on the next request, keeping the 12 most recent tool uses, if that frees at least 20,000 tokens <span class="td-ev">bin</span>. 3,900 seconds is 65 minutes, five minutes past the longest cache lifetime. My reading of the constant is that it only clears when the cache is already gone, so the rewrite was going to happen anyway and might as well be smaller.

<span class="td-h cx">Codex</span> does neither. OpenAI's cache is managed by the provider with no separate write fee, so there's nothing comparable to optimize.

Play with it and pi's warming turns out to be rare by design. At $3 per million input tokens with a 5-minute cache, a refresh only pays off in expectation above roughly 230K tokens of context. Warming exists for big contexts on expensive models and, mostly, for the case where the agent is busy running a long tool call (pi assumes certain continuation then, and allows up to 60 minutes).

## Paying for tools you never call

Tool definitions are part of the prompt. A server with a few dozen tools can cost thousands of tokens on every request before the model does anything. All three harnesses now avoid sending MCP tool definitions up front, each in a different way.

- <span class="td-h cx">Codex</span> registers MCP tools as deferred whenever the model supports tool search, which every bundled model does. The model sees namespaces and a `tool_search` tool that runs BM25 over tool metadata and returns up to 8 matches <span class="td-ev">src</span>.
- <span class="td-h cc">Claude Code</span> defers every MCP tool by default and lists only their names; a ToolSearch tool loads full schemas on request, using Anthropic's server-side tool search <span class="td-ev">bin</span> <span class="td-ev">docs</span>. A server can opt out with `alwaysLoad`.
- <span class="td-h pi">pi</span> goes further by default: MCP tools aren't declared to the model at all. It gets one `codemode` tool and writes JavaScript that calls them <span class="td-ev">src</span>. Deferred search and direct declaration are config options.

Skills get the same treatment everywhere: only a name and short description go into the prompt, and the model reads the full instructions when it needs them. The caps differ. Codex gives the catalog 2% of the window and cuts descriptions at 1,024 characters. Claude Code gives it 1% (8,000 characters at 200K) and cuts at 1,536 characters. pi lists everything with a file path and lets the model read the file.

## Subagents

A subagent is the cleanest context tool there is: do noisy work in a separate window and bring back only the conclusion. The question is how much of the parent's window the child starts with.

<TD id="f-sub" />

<span class="td-h cx">Codex</span>'s fork is the most surgical. The child gets the parent's messages, including final answers, but every tool call, tool result and reasoning item is stripped <span class="td-ev">src</span>. That makes the child small and well-informed, but it can reuse the parent's cache only up to the first stripped item; after that the prefix is different. A newer option, `preserve_fork_prefix`, keeps everything for exactly that reason. Defaults allow up to 6 child threads, one level deep.

<span class="td-h cc">Claude Code</span> offers the two ends. A subagent starts fresh, with its own prompt, the task, CLAUDE.md and git status, and returns only its final report <span class="td-ev">docs</span>. A fork inherits the parent's full history and system prompt, so its first request is mostly a cache read.

<span class="td-h pi">pi</span> doesn't ship subagents. The README lists them as deliberately skipped. An example extension spawns separate `pi` processes in JSON mode with no session, which is about as isolated as a child can be.

## On disk

All three write sessions as JSONL, one event per line, and all three can resume. What differs is how a compaction is recorded and how much of the file has to be replayed to rebuild the context.

<TD id="f-disk" />

- <span class="td-h cx">Codex</span> writes rollouts to `~/.codex/sessions/…/rollout-…jsonl`. A compaction is a `Compacted` item carrying the full replacement history, so resume finds the last one and replays only what came after <span class="td-ev">src</span>.
- <span class="td-h cc">Claude Code</span> writes `~/.claude/projects/<cwd>/<session>.jsonl`. A compaction is a `compact_boundary` system record with `parentUuid: null`, which cuts the message chain, followed by the summary message. The record also lists tools that had been loaded on demand, so they stay loaded across the boundary <span class="td-ev">bin</span>; I checked this format against transcripts on disk.
- <span class="td-h pi">pi</span> writes a tree: every entry has an `id` and `parentId`. `/tree` moves between branches in the same file and can summarize the branch you leave. Context is rebuilt by walking from the current leaf to the root and starting at the latest compaction on that path <span class="td-ev">src</span>.

## All of it at once

Each section so far isolated one mechanism. In a real session they interact: how much a tool's output is cut decides how fast the window fills, which decides how often compaction runs, which decides how much of the cache is thrown away. This last figure runs one session through all three harnesses with every rule from this page switched on.

All three run on the same model at the same prices, so the comparison is about the harness. Two simplifications favor Claude Code and should be kept in mind: every tool call is treated as a shell command, which is where its 30,000-character cap applies, and going back to read a saved output file costs nothing.

<TD id="f-all" />

Both tool-heavy sessions show the same pattern, and it comes from a rule that has nothing to do with compaction. In this model Claude Code compacts roughly half as often as the other two, and writes far fewer tokens to the cache. Claude Code replaces any command output over 30,000 characters with a 2KB preview, so a 150KB test log costs it about 500 tokens. Codex keeps 10,000 tokens of the same log and pi keeps 12,800. Outputs between 30,000 characters and 50KB are where the gap is widest: Claude Code previews them, while Codex and pi keep up to 10,000 and 12,800 tokens of each. The trade runs the other way too. A model under Claude Code has to go and read the file to see what it skipped, and this simulation doesn't charge for that call. If the model needs the middle of most outputs, the advantage shrinks or reverses. Running one scripted task through all three tools and plotting their real token usage would settle it. I haven't done that.

In the conversation-heavy session the three converge, because there's little tool output to cut. What's left is the trigger arithmetic from the first section and what each keeps after a compaction.

## What I'd take from each

From <span class="td-h cx">Codex</span>: keep the user's own words through compaction. The rule that recent user messages survive verbatim is cheap and protects the one thing a summary is most likely to blur, which is what was asked.

From <span class="td-h cc">Claude Code</span>: re-read state instead of remembering it. Re-attaching files from disk after a compaction gives the model current file contents, and saving oversized output to a file keeps it within reach without spending context on it. The idle clearing, timed just past the cache lifetime, is the most cost-aware constant in any of the three.

From <span class="td-h pi">pi</span>: edit the summary in place, and keep a real tail of conversation. The update prompt is a few lines of text, and I suspect it does more for coherence in long sessions than any threshold tuning.

All three already agree on one thing: append, never edit. Each has rearranged its prompt so that changes arrive at the end, which is what taking the cache seriously looks like in practice.
